# 多链接 / 同系列：批量取稿与体系化梳理编排

> 被 `../SKILL.md` 的"C. 多链接/同系列"按需引用。单条视频如何按作者角色成文，看 `article-pipeline.md`；本文件只解决"一次给多个链接、且它们相关"时多出的那部分工作：**先成体系，再动笔，不做 N 篇流水账；并在一开始就预判落库时的结构治理**。

## 1. 什么时候算"系列/批量梳理"，而不是 N 个独立任务

出现以下信号之一，就按本文件走，而不是对每条链接各跑一遍单视频流水线：

- 一次给 ≥2 个链接，且是**同一作者 / 同一频道 / 同一播放列表**；
- 用户说"这几个强相关""一个体系分着讲""整理到一起""重新编排""形成知识库/一篇"；
- 标题共用同一前缀（如"跟着 XX 学…"EP1/EP2）、或主题指向同一个大问题。

反之，几条链接主题互不相关、用户只想各自存稿/成文，则退回 `fetch_for_article.py` + `article-pipeline.md` 逐条处理。

## 2. 第一步永远是批量探查总览（先看清结构，再决定取稿）

```bash
python3 "<skill>/scripts/batch_fetch.py" "<url1>" "<url2>" ... -o series-fetch
```

脚本对每条只解析、不盲目下媒体，产出 `series-overview.md/.json`：按上传日期排序的表（标题/UP/时长/语言/字幕/章节数/字数）、**同作者检测**、建议阅读顺序；有字幕的直接下字幕并**按视频自带章节切成结构化稿**（`transcripts/<id>.md`），无字幕的标 `needs-fetch_for_article`（加 `--with-audio` 才委托单条流水线下载转写，避免一上来拉一堆大文件）。

先据总览判断四件事，再动笔：

1. **关系**：是依赖递进（后集建立在前集上）还是并列专题？递进→阅读/讲解顺序通常=上传顺序；并列→按主题聚类。
2. **完备性**：语言/字幕是否齐、有没有缺章节或缺稿的条目，先补齐。
3. **粒度**：信息密度是否足以让每集独立成文（决定第 4 节"合一篇还是拆多篇"）。
4. **落库位**（结构治理前置）：这批内容将来要进哪个知识库/目录？先粗看目标库**现有节点树与导航/索引**，预判它属于哪个主题域、会和哪些**已存在**条目同簇——不要等写完才发现无处可放或与旧文重复（详见第 5 节）。

> 多语言音轨要锁原声、避开 AI 自动配音等选流问题，见 `platform-strategy.md` 第 4 节，不在此重复。

## 3. 取稿：字幕优先、按章节，缺口走单条流水线

- 系列讲解类视频作者大多自带 chapters，**按章节切的稿比按字数切段更利于体系化**（章节=作者亲自划的知识边界），`batch_fetch.py` 已默认这么做。
- 手动字幕最可靠；自动字幕经去滚动重复后仍要通读校专有名词/同音字（错字表见 `transcribe-and-translate.md`）。
- 无字幕的个别条目：对它单跑 `fetch_for_article.py`（字幕>最小音频>可 OCR 视频），补齐后再一起分析，不要让一条缺口拖住整批。

## 4. 体系化编排（核心，单视频流水线不覆盖）

**先通读全部章节稿、画出体系地图再写**，不要边读边写。

1. **抽主线、分层级**：把跨集内容重组成"是什么 → 基本原理 → 内部机制 → 能力扩展 → 实战/对比"这类递进层；识别 1~2 条主线把各集串起来（例：一条"运行时内核"主线 + 一条"能力扩展/检索"主线，后者是前者机制的落地）。
2. **合一篇 vs 拆多篇**：

   | 倾向合一篇综述 | 倾向拆多篇（互相链接） |
   | --- | --- |
   | 强耦合递进、共同回答一个大问题 | 各集主题独立、可被单独检索消费 |
   | 单集密度不足以独立、需彼此上下文 | 面向不同读者/任务场景 |
   | 用户要"一篇看懂整个体系"、便于入库 | 合集会过长（如 >1.5 万字）难阅读 |
   | 集数不多（约 ≤8）且总时长可控 | 子主题各自还会持续更新、需独立维护 |

   拿不准时：**同一作者的连续体系讲解默认合一篇**（读者要的是体系，不是分集摘要），并在文首给"学习路径图"。
3. **横向提炼，避免重复**：跨集反复出现的概念/机制（如同一个运行框架、同一条机制链）抽成"横向命题/总图"讲一次，各集只讲它在该集的增量，不在每集重复定义。
4. **与已有知识库对齐，而非孤立追加**：检索已入库的相关条目，显式建立关系——本篇是哪条的**源码级深化 / 上下游互补 / 原理印证**；据此决定挂载节点、主标签与交叉链接。**是否需要调整节点层级/新建簇，属第 5 节结构治理，先评估再动**；改旧条目正文属高扩散变更，先列影响再动。
5. **事实分级、不脑补**：区分【视频：作者所述】【归纳：跨集综合，可能带整理者判断】【对接：与本站/外部资料的关联】；视频没给的仓库 URL、版本号、数据一律不臆造，标"不确定/待核"；作者给的对比数字要注明"非严格基准"等原限定。

## 5. 落库的结构治理预判（多链接天然是"成簇"内容）

一次给多条 = 一批**成簇**内容。落库不是"再多挂一篇"，动笔前就要带着结构意识，避免随手平铺、攒乱了再返工。

- **两条轴解耦，别混用**：
  - **归档轴**（领域标签/分类树）：一篇一个主标签、位置稳定，**不为阅读便利硬搬物理位置**；跨标签的强相关用"跨链"或快捷方式引用。
  - **阅读轴**（主题/学习路径）：用章节簇、导航/目录页表达"先读什么、谁和谁相关"，是叠加层，不破坏归档。
- **三种落库形态，按耦合度选**：
  1. **合成一篇章节式长文**：强耦合递进、共同回答一个大问题（如 8 集 → 1 篇综述），文内用章节/学习路径图组织。
  2. **父子层级 / 主题簇**：某个分类下平铺到约 ≥7 篇、或出现清晰子主题时，建"章节簇页"（本身是导读，含本簇阅读顺序+每篇一句），把同主题文章移入；簇内顺序=学习路径。
  3. **导航/目录页**：相关条目分散在多个标签/层级时，建一篇导航把它们按主题域串起，物理归档不动。
- **全量重组的触发阈值**（命中就值得做一次轻量迭代，而不是继续打补丁）：某分类平铺难读（约 ≥7 篇）；同一概念在 ≥2 篇重复定义、读者要自己拼；缺少统一入口、不知道先读什么；新内容无处可放只能硬塞。
- **重组手法保持可逆、低破坏**：以"新增导航/簇页 + 移动节点归位"为主，**不删原文、不改主标签、保留按时间的索引台账**；移动是可逆的。改前先列"现状树 → 目标树"映射，改后回读验证。
- **落库后回读验证**：节点层级正确、簇内顺序即学习路径、导航链接全覆盖且无死链、时间索引台账已同步登记。

## 6. 交付前检查

- 每集的关键结论都能回溯到对应 `transcripts/<id>.md` 的某一章，无凭空内容；
- 主线覆盖**全部**条目、无遗漏集，总览表里每条都在成文中有落点；
- 同一术语/版本号/日期/数字在全篇一致，合集总字数与总时长相称（中文口播约 250–320 字/分钟可作下限参考）；
- 入库条目按既有规范登记索引（倒序、主标签、来源、价值评级、文档链接），并按第 5 节确认挂载层级、簇/导航是否需要同步，最后回读验证挂载位置与索引顺序。

## 7. 与单视频流水线的分工

- 单条视频 → `fetch_for_article.py` 取稿 + `article-pipeline.md` 按作者角色成文；
- 多条相关视频 → 本文件：`batch_fetch.py` 批量取稿/按章节 + 本文件做体系化编排与第 5 节落库结构治理；二者的清洗、翻译、转写规范共用，不重复维护。
